# 单用户平台需求基线（D1）

> 日期：2026-11-02
> 状态：D1 草案，作为 D2 平台契约与后续验收的输入。
> 使用边界：**单用户、多任务、多沙箱、单机控制面**。

## 1. 目标


平台需要证明的不是“能启动一个子进程”，而是：

- 有稳定、可演进的 API / SDK 与明确错误语义；
- 有节点、调度、生命周期、取消、回收和对账能力；
- 有结构化 trajectory、Log / metrics / trace；
- 有压测、背压、故障注入和实测 SLO。

## 2. 三个个人开发痛点

### 痛点 1：聊天与长任务执行耦合，缺少流式反馈和统一取消

**现状证据**

- `src/chat_secure_api.py:315-622` 的 `/chat` 是同步请求—响应；模型执行完成后才返回完整 `reply`。
- `src/chat_secure_api.py:488-502` 在请求处理过程中直接调用 `legacy_chat.chat()`。
- `src/agent.py:1541-1653` 的 `chat()` 一次完成模型调用、工具执行和最终回答，没有面向调用方的取消令牌或执行状态。
- `docs/AGENT_TOOLS.md:73-92` 记录了当前“两段式固定形状”：一次工具决策、一次最终收口。

**平台能力**

- 建立 `run / step / exec` 执行模型，助手与执行层解耦。
- 提供 SSE 流式输出、Esc / 客户端断开取消。
- 将取消传递到平台 exec 和 runner，最终终止进程树并记录 `cancelled`。
- 保留现有 request_id 幂等、准入和预算保护思路，不推倒重来。

**验收方向**

断流后不只是 HTTP 连接关闭：工具执行进入取消状态，runner 无残留进程，轨迹可查询最终状态。

### 痛点 2：工具在助手进程内直接执行，缺少统一隔离与生命周期

**现状证据**

- `src/agent.py:1394-1486` 直接分发并执行提醒工具。
- `src/agent.py:1611-1638` 在聊天流程内执行工具并把结果回填模型。
- 当前硬约束主要是工具名白名单、参数校验、身份校验和单轮调用上限，见 `docs/AGENT_TOOLS.md:129-150`。
- 当前没有统一的 `create / exec / timeout / cancel / destroy / reclaim` 沙箱接口。

**平台能力**

- 建立工具注册表和 allow / ask / deny 审批矩阵。
- 所有 read / write / ls / shell / python / http 工具统一经过平台 exec。
- tier1 先提供受控执行：工作区限制、环境变量清洗、超时、输出上限、取消和进程树清理。
- tier2 再验证容器隔离；不能把 tier1 process 宣称为强安全沙箱。
- 保留提醒工具现有的参数语义、身份绑定和副作用上限，不因平台化而放宽。

**验收方向**

搜索不到宿主直跑路径；每个工具都有 exec 记录；路径穿越、符号链接、环境变量泄露、输出超限和取消都有负向测试。

### 痛点 3：已有 span 与用量审计，但缺少面向工具执行的正式 trajectory 数据模型

**现状证据**

- `src/core/trace_store.py:55-217` 已能保存 `trace_id / span_id / parent_id / name / status / attrs`。
- `src/main.py:60-116` 已为 HTTP 请求建立 trace。
- `docs/AGENT_TOOLS.md:154-160` 记录模型调用的延迟、结束原因和工具名，但有意不记录工具参数。
- 当前没有统一的 `run_id / step_id / exec_id / schema_version` 工具轨迹，也没有跨 runner 的事件顺序和最终状态契约。

**平台能力**

- 定义 trajectory schema v1，关联 run / step / exec，记录工具请求、结果、错误、时间与最终状态。
- 延续现有“用量审计不记录敏感参数”的取舍；trajectory 需要记录工具参数时，必须另设脱敏和保留规则。
- 打通 Log / metrics / trace，并支持按 run 导出 JSONL。
- 不接入真实训练 pipeline，不承诺 trajectory 回放；本周期只证明可靠记录、校验、查询和导出。

**验收方向**

一句话触发多个工具后，可以按 run 查看每个 step 和 exec，导出顺序可校验的 JSONL，并从同一 trace 找到助手、平台和 runner 证据。

## 3. 必须保留的现有资产

| 资产 | 保留原因 |
| --- | --- |
| `chat_secure_api` 的 request_id 幂等、并发准入、预算与归属校验 | 可直接作为平台 API 契约和错误语义的现有参考 |
| 提醒工具的白名单、参数上限、身份绑定和副作用限制 | 已有服务端硬约束，不应在沙箱改造中退化 |
| `scripts/run_guarded_tests.py` 与临时数据目录 | 可继续作为测试隔离基础，但不把它当成 OS 沙箱 |
| `core/trace_store.py` / `trace_context.py` | 可复用现有 span 存储与请求关联能力 |
| SQLite 与单机部署 | 符合单用户边界，避免为本期目标引入额外基础设施 |

## 4. 明确不做

- 不新增或重构登录、账号、多租户、计费体系；现有认证与额度代码保持可用，不作为本期展示重点。
- 不做真实多机集群、raft / etcd / 2PC。
- 不做子代理、技能系统、MCP、多模态和知识库重构。
- 不做 warm pool，不统计池命中率。
- 不做 trajectory 回放或真实模型训练接入。
- 不在 tier1 上承诺不可信代码安全隔离。
- C++ 与 Docker 按阶段门推进，不能挤占核心平台链路。

## 5. D40 展示结果

最低可接受展示由三部分组成：

1. **基本链路**：一句话触发多个工具，展示 API、调度、沙箱状态和 trajectory。
2. **可靠性**：演示取消、TTL、节点失效或对账中的至少一种真实故障路径。
3. **性能与退化**：展示 RPS 阶梯下的延迟、错误率、背压与饱和拐点。

成功口径是“真实实现 + 可复跑证据”，不是前端页面数量，也不是模拟生产规模的旁白。
